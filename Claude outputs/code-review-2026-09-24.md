## 5. Оценка работы разработчиков

По журналу git все коммиты с 7 сентября сделаны от одной учётной записи (`35windmill35`). Ранние тестовые коммиты второго участника вычищены. Оцениваю работу команды в целом.

**Оценка: 6 / 10.** Код — уровень сильного middle, процесс и управление качеством — junior.

**Сильные стороны**

- **Производительность.** За 17 дней сделаны три экрана, векторный PDF для всех экранов, детализация, CSV, синхронизация фильтров со ссылкой, сессии, частичные отказы баз, полный редизайн. Для одного исполнителя объём большой.
- **Инженерные решения.** Эпохи сессии и загрузки, `AbortController`, stale-while-revalidate, «эффективные» значения фильтров через геттеры, `null` вместо «0%», постраничная загрузка с дедупликацией. Всё это сделано правильными механизмами, а не заплатками.
- **Чистота кода.** Строгий TypeScript без ошибок, ESLint без замечаний, FSD-слои не нарушены, расчёты отделены от UI.
- **Внимание к пользователю.** Экраны состояний, прогресс загрузки по базам, «Показать данные» у графиков, клавиатурная доступность.

**Слабые стороны**

- **Приоритеты.** Между ревью 21.09 и сегодняшним днём сделан большой редизайн, но не закрыт ни один из блокеров прошлого ревью (P0-3, P0-6, N-1, N-2). Самые дешёвые из них (N-1, P1-7, P1-8, P0-3 «скрыть») занимают по полдня. Если редизайн — прямое требование заказчика, это оправдывает очерёдность, но не отказ от S-задач по безопасности.
- **Тестов нет как практики.** После трёх ревью в репозитории 0 тестов, хотя готовый стартовый набор передавался 21.09. Каждый новый коммит может незаметно сломать расчёт.
- **Релизный процесс.** Пуши прямо в `main`, которые сразу уходят в прод. Сообщения коммитов вроде «Правка» ×3 и «Исправления» не описывают изменений. Сломанный CI не чинится третью неделю.
- **Контракты с бэкендом.** `DBIndex` и справочник причин по-прежнему «угаданы». По `Offset` контракт наконец получен — это правильный путь, его нужно продолжить.
- **Повторы.** Переход на Rubik в PDF снова без казахских букв, хотя это было записано в двух ревью. Нужен чек-лист «что проверить при замене шрифта или подмножества».

**Рекомендации команде**

1. Правило: в спринте сначала P0 и S-пункты безопасности, потом фичи и дизайн.
2. Защитить `main`, работать через PR, мёрж только при зелёном CI.
3. Каждый исправленный дефект закрывать тестом.
4. Сообщения коммитов в формате «что и зачем» (`fix(csv): экранирование формул`).
